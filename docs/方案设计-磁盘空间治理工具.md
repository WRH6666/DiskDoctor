## 一、竞品调研（GitHub 与开源生态）

### 1.1 空间分析类 —— "看清空间去哪了"

| 项目 | 技术栈 | 扫描原理 | 亮点 | 硬伤 |
|---|---|---|---|---|
| **WinDirStat**（GPLv2，活跃） | C++ / MFC / Win32 | `FindFirstFileEx` 递归遍历目录树 | Treemap + 目录树 + 扩展名三视图；NTFS 快速扫描；重复文件哈希；**文件系统变动监控**；CSV 导入导出；内置 cleanmgr/DISM/CHKDSK/影子副本等**清理快捷入口** | 1TB 盘扫描 15–30 分钟；每文件建对象，百万文件级内存吃紧；MFC 老框架，treemap 大数据量卡顿；**纯"看"，没有"该不该删"的知识** |
| **WizTree**（闭源，个人免费） | C++ | **直接读 NTFS `$MFT`**，绕过 OS API | 比 WinDirStat 快 22–46 倍（1TB < 1 分钟）；正确处理硬链接，总量与资源管理器一致；treemap + 文件列表 + 重复文件；MFT/CSV 导出可做历史对比 | 闭源；仅 NTFS 走快通道；需管理员权限；每次都是全量重扫，无增量；同样没有清理知识层 |
| **TreeSize**（商业） | C++ | API 遍历 / MFT | 计划任务、阈值告警、HTML/CSV 报表，企业审计向 | 收费；无"清理决策"能力 |
| **SpaceSniffer** | C++ | API 遍历 | Treemap 边扫边渲染，热点很快可见 | 只做可视化，无报表无删除 |
| **dust**（Rust） | Rust + rayon | 递归遍历 + **并行聚合** | 输出"直觉化"：树 + 条形图，一眼看出谁占大头；代码质量高 | 无 GUI、无 treemap、无快照、无删除 |
| **dua-cli**（Rust） | Rust + petgraph | 并行遍历 + 图结构聚合 | **交互式 TUI 可浏览可删除**；`.gitignore` 风格忽略文件；可输出 flamegraph | 交互模式仅适配深色终端；**中文字符宽度计算有 bug**；100 万条目约 60MB 内存；受 `u32` 节点上限约束 |
| **ncdu**（C） | C + ncurses | 单线程遍历 | 极省资源；`-o json` 导出可做**快照对比**；SSH/容器场景无敌 | 无图形可视化；扫描偏慢 |
| **gdu / diskonaut / darya / leaves** | Go / Rust | 并行遍历 | 终端内 treemap，各有取舍 | 单点工具，无清理闭环 |
| **MangoDisk**（Tauri + Rust，3k star，近 30 天涨 1.8k） | Rust + Tauri | 元数据扫描 + 规则库 | **安全优先**：缓存清理 / 大文件 / 重复文件 / treemap / 应用卸载 / 启动项 / 系统优化 / **操作历史**；规则库丰富 | 无 Linux；只有手动下载；规则偏"通用型"，对中国用户的本土重灾区（微信/QQ/WPS/网盘）覆盖不足 |
| **d-space**（Tauri v2 + Vue3 + Rust，早期） | Rust + Tauri | **MFT 快速扫描** | 三个想法很好：**0–100 可删安全评分**、**暂存区 + 两阶段提交**、**撤销保障** | 项目太早期，功能不完整 |

### 1.2 重复/垃圾发现类 —— "找出冗余"

- **Czkawka / Krokiet**（Rust，30k+ star，MIT）：同类中最完整的。**10 种扫描模式**——重复文件（名/大小/哈希）、相似图片（感知哈希）、相似视频（逐帧）、同音乐（标签）、空文件夹、空文件、临时文件、大文件、坏扩展名、损坏文件、无效软链接、EXIF 批量清除。多线程 + **扫描缓存**（二次扫描极快）+ JSON 输出 + CLI/GTK4/Slint 三前端。
- **fclones / rmlint / jdupes**（Rust/C）：纯去重，无 UI。
- **dupeGuru**（Python）：同类里最慢的代表。

### 1.3 清理执行类 —— "动手删"

- **BleachBit**（开源）：Linux/Windows 通用清理规则引擎，但规则面向"通用垃圾"。
- Windows 原生：存储感知、`cleanmgr`、`DISM /StartComponentCleanup`、VSS 影子副本管理。

### 1.4 调研结论：现有方案有三个共同的空白

**空白一：'看见' 与 '该不该删' 之间是断的。**
所有工具都在回答"哪里大"，没有一个回答"这里大，**能不能删、删了会怎样、该怎么删才不出事**"。用户拿到一张漂亮的 treemap，依然不敢下手 —— 这才是"硬盘满了却清不动"的真实卡点。

**空白二：只有一次性快照，没有时间维度。**
没人回答"这个月谁涨了 20GB""为什么这个目录每周涨 3GB"。后果是：清完还会涨回来（`node_modules`、日志、Docker vhdx、浏览器缓存），用户陷入"反复清理"的循环。

**空白三：系统级"隐形占用"完全不可见或不敢碰。**
在 Windows 上，真正的空间黑洞往往不是垃圾文件，而是这几类 —— 常见总量 20–50GB：

| 项目 | 典型占用 | 正确做法 | 现有工具的处境 |
|---|---|---|---|
| `hiberfil.sys` 休眠文件 | ≈ 内存的 40–100%（8–32GB） | `powercfg /h off` 或 `/type reduced` | 删了可能蓝屏；工具只显示大小，不给安全开关 |
| `pagefile.sys` 页面文件 | RAM 的 1–1.5 倍 | 迁到其他盘或设固定值 | 同上，绝对不能直接删 |
| `System Volume Information`（VSS 还原点/影子副本） | 几 GB – 几十 GB | `cleanmgr` → 清理系统文件 | 普通扫描**看不见**（无权限） |
| `WinSxS` 组件存储 | 5–15GB（硬链接仓库） | **只能** `DISM /StartComponentCleanup` | 手动删 = 系统无法启动 |
| `DriverStore\FileRepository` | 可达 10GB | 官方工具清旧驱动 | 不敢碰 |
| `Windows.old` | 20–50GB | `cleanmgr` | 一处**可回收几十 GB** 的地方 |
| WSL2 `ext4.vhdx` / Docker Desktop vhdx | 20GB+ | `compact` / 手工压缩 | 在资源管理器里**不计入占用**，用户完全找不到 |
| `AppData\Local` 各类缓存（npm/pip/conda/IDE/浏览器） | 几 GB – 几十 GB | 各包管理器自有 cache clean | 看得见但不知道哪个能清 |

**空白四：清理动作本身不安全。** 现有工具要么一键删（风险高），要么只能手动在资源管理器里删（无撤销、无记录）。

## 二、方案定位

> **不做"第 N 个 treemap 查看器"，做"硬盘体检 + 归因 + 安全清理"的一体化工具。**

三个差异化支点，正好对应上面四个空白：

1. **知识层** —— 每一坨空间都附带「这是什么 / 能不能删 / 删了会怎样 / 正确操作方式 / 预计回收多少」。把工具从"CT 机"升级成"医生"。
2. **时间维度** —— 快照留存 + 增量 diff，回答"这个月谁涨最多"，并给出"防止再涨"的建议（如改缓存目录、加忽略规则、定时清理）。
3. **安全执行** —— 暂存区 + 两阶段提交 + 一键撤销。默认不删；绿灯项才可批量操作；系统级项目只走官方命令。

## 三、系统架构

### 3.1 分层设计

```
┌───────────────────────────────────────────────────────────────┐
│ 6. 交互层  Tauri 2 WebView (React + TS)                        │
│    · 体检报告首屏（按安全等级分组的一键优化清单）                  │
│    · Treemap(Canvas/WebGL) + 目录树 + 文件列表                   │
│    · 时间轴对比视图 · 清理预览与撤销                              │
├───────────────────────────────────────────────────────────────┤
│ 5. 执行层  Executor                                            │
│    · 暂存区 + 两阶段提交 + 撤销日志                               │
│    · 回收站优先 / 同卷 rename 隔离 / 跨卷复制校验后删              │
│    · 系统级操作封装：powercfg · DISM · cleanmgr · vssadmin        │
├───────────────────────────────────────────────────────────────┤
│ 4. 决策层  Knowledge & Safety                                  │
│    · 可删安全评分 0–100 · 后果说明 · 正确操作方式                  │
│    · 危险区黑名单（WinSxS / System32 / Program Files / pagefile） │
├───────────────────────────────────────────────────────────────┤
│ 3. 分析层  Analyzer                                            │
│    · 目录聚合树 · 快照 diff · 重复文件三级漏斗(大小→前缀→Blake3)   │
│    · 类型/年龄/归属聚合 · **归因规则引擎**（路径→归因类别）        │
├───────────────────────────────────────────────────────────────┤
│ 2. 存储层  Index Store  (SQLite / LMDB)                        │
│    · 快照：路径·逻辑/物理大小·mtime·FRS/inode·扩展名·硬链接去重    │
├───────────────────────────────────────────────────────────────┤
│ 1. 采集层  Scanner（多后端，可降级）                             │
│    ① NTFS MFT 直读（Windows，提权）→ 秒级全盘                    │
│    ② USN Journal 增量 → 后续扫描亚秒级                          │
│    ③ 通用并行遍历（rayon）→ 跨平台 / 非 NTFS fallback            │
│    ④ 系统特殊对象采集器 → hiberfil/pagefile/VSS/WinSxS/vhdx     │
└───────────────────────────────────────────────────────────────┘
```

### 3.2 关键技术选型

| 决策点 | 选择 | 理由 |
|---|---|---|
| 桌面框架 | **Tauri 2** | 装机包 ~10MB、空闲内存 60–120MB（Electron 90–150MB / 250–500MB）。**一个清理空间的工具自己不该占空间**，这是产品自卫逻辑。安全上 Tauri 默认白名单权限模型，比 Electron 更契合"高危文件操作"场景 |
| 核心引擎 | **Rust**（独立 crate 分层） | 扫描/哈希性能；内存安全（避免 C++ 那类内存泄漏）；`rayon` 并行；`blake3` 高速哈希 |
| MFT 解析 | `ntfs-reader`（含 USN journal）或 `mft` crate | 已被验证可直读 `\\.\C:` 的 `$MFT`，且自带 USN 日志读取；`uffs-mft` 的工程经验可直接借鉴：**自适应并发**（NVMe 32 / SSD 8 / HDD 2）、**4MB 大块 I/O**、**并行解析**、**bitmap 跳过空闲记录（省 30–50% I/O）**、**零拷贝 fixup** |
| 增量刷新 | **USN Journal** | 与 Everything 同源思路：首次全量建索引，之后监听变更日志做增量，CPU/磁盘开销极低 |
| 前端渲染 | **Canvas / WebGL treemap** | 百万级节点绝不能走 DOM/SVG，否则重演 WinDirStat 的卡顿 |
| 本地存储 | **SQLite**（快照 + 规则库 + 操作日志） | 单文件、可 diff、可导出、生态成熟 |
| 归因规则库 | **YAML/JSON 数据文件 + 路径/扩展名/签名匹配** | 规则与代码解耦，用户可自行扩充（本土 App 覆盖是护城河） |
| 提权 | 应用内 **UAC 提权** + 无权限时自动降级到遍历后端 | 保证"能用"和"好用"两个档位 |

## 四、分期实施

### P0 · 只读体检（先验证价值，不做任何删除）
1. Scanner：NTFS MFT 直读后端 + 通用遍历降级后端
2. Index Store：快照落库
3. Analyzer：目录聚合树、类型/年龄聚合、**归因规则引擎（首批 60–80 条规则）**
4. Decision：安全评分 + 后果说明 + 危险区黑名单
5. UI：**体检报告首屏** + Treemap + 目录树 + 文件列表

> 验收标准：在你的机器上跑一次，首屏直接给出"可安全回收 X GB，其中这几项占大头"，且每项都说清是什么、为什么能删。

### P1 · 增量与执行
- USN Journal 增量刷新（第二次扫描亚秒级）
- 重复文件三级漏斗（大小 → 前缀 4KB 哈希 → Blake3 全量）
- 快照 diff 时间轴视图（"这 30 天谁涨了"）
- 暂存区 + 两阶段提交 + 撤销
- 一键清理（**仅绿灯项**）：包管理器缓存、浏览器缓存、临时文件、回收站、崩溃转储、旧安装包

### P2 · 系统级与自动化
- 系统隐形占用专模块：VSShadows / WinSxS / DriverStore / hiberfil / pagefile / WSL·Docker vhdx
- 官方命令封装与回显（执行前预览命令、执行后验证结果）
- 定时巡检 + 报告导出（Markdown/HTML）
- 可选：AI 辅助解释未知大文件（**本地脱敏，只传文件名与路径特征，需显式开启**）

## 五、风险与对策

| 风险 | 对策 |
|---|---|
| MFT 直读需管理员权限，部分安全软件拦截 | 应用内 UAC 提权；失败自动降级遍历后端并提示；不常驻服务 |
| **删除操作是本产品命门** | 默认不删；暂存区隔离 + 两阶段提交 + 一键撤销；危险区硬黑名单；每次操作前预览"将删除 N 项、回收 X GB、可撤销" |
| 硬链接导致重复计算 | 按 FRS/inode 去重（WizTree 的正确性优势必须继承） |
| 稀疏文件 / NTFS 压缩 / 长路径 / 中文字宽 | 逻辑大小与物理大小分列显示；长路径用 `\\?\` 前缀；前端避免终端字符宽度陷阱 |
| WebView2 在旧版 Win10 缺失 | 安装包内置 bootstrapper |
| 规则库误判导致误导 | 规则带来源与说明；不确定的一律标黄并要求人工确认，绝不标绿 |
| 隐私 | 纯本地；无遥测；AI 功能默认关闭 |
